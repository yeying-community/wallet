# 钱包身份 V1 跨仓库契约

> 状态：V1 实现契约，尚未上线。
>
> 关联设计：[钱包身份协议与数据模型](./钱包身份协议与数据模型.md)
>
> 适用仓库：Wallet、Node、web3-bs、Project、Router、Social。

## 1. 契约范围

本文件只定义跨仓库必须一致的对象、字段、签名域、接口形状和错误语义。交易、资产、应用权限、邮箱投递模板和具体数据库表不属于本契约。

正式实现不得出现以下外部字段或概念：

- `subjectId`
- `sub_xxx`
- Node Passport subject
- 以钱包地址作为身份主键
- 以用户名或邮箱作为身份主键

正式身份主键只有：

```text
walletIdentityId: wid_<base64url-random>
did: did:yeying:<walletIdentityId>
```

## 2. 固定常量

```text
DID_METHOD                 = did:yeying
IDENTITY_ID_PREFIX         = wid_
IDENTITY_ID_RANDOM_BITS    = 128 minimum
IDENTITY_DOCUMENT_VERSION  = 1
SIGNATURE_ALGORITHM        = Ed25519 / EdDSA
CANONICALIZATION           = RFC 8785 JCS
CREDENTIAL_FORMAT          = compact JWS JWT-VC profile
ISSUER_DISCOVERY           = did:web + HTTPS JWKS
CREDENTIAL_DEFAULT_TTL    = 24h
CREDENTIAL_MAX_TTL        = 7d
HIGH_RISK_STATUS_MAX_AGE   = 5m
LOW_RISK_STATUS_MAX_AGE    = 1h
CONTROLLER_CHANGE_DELAY    = 24h
V1_MANAGE_THRESHOLD        = 1
```

时间全部使用 RFC 3339 UTC；JWT 数值时间使用 Unix seconds。所有随机数使用密码学安全随机源。

## 3. 身份文档

### 3.1 公开字段

```json
{
  "version": 1,
  "id": "did:yeying:wid_example",
  "walletIdentityId": "wid_example",
  "createdAt": "2026-08-13T00:00:00Z",
  "updatedAt": "2026-08-13T00:00:00Z",
  "revision": 1,
  "controllers": [],
  "accounts": [],
  "issuers": [],
  "recovery": {
    "version": 1,
    "manageThreshold": 1,
    "controllerChangeDelaySeconds": 86400
  }
}
```

私密材料永远不在公开文档中。文档只存公钥、控制器用途、账户地址、issuer 元数据和撤销信息。

### 3.2 文档签名

签名输入：

```text
JCS(documentWithoutProof) UTF-8 bytes
```

签名对象：

```json
{
  "type": "YeyingIdentityDocumentProofV1",
  "created": "2026-08-13T00:00:00Z",
  "verificationMethod": "did:yeying:wid_example#controller-1",
  "purpose": "assertionMethod",
  "proofValue": "base64url(ed25519-signature)"
}
```

验证方必须检查：DID、`verificationMethod`、控制器状态、控制器用途、`revision`、签名和时间窗口。

## 4. 链账户关联

### 4.1 账户模型

```json
{
  "accountId": "acct_01",
  "chainKey": "eip155:1",
  "family": "evm",
  "address": "0x0000000000000000000000000000000000000001",
  "publicKey": "optional-chain-public-key",
  "controllerId": "controller-1",
  "status": "active"
}
```

`chainKey + address` 只标识链账户；`did:yeying:*` 才标识钱包身份。

### 4.2 关联证明

```json
{
  "version": 1,
  "purpose": "identity-account-link",
  "identity": "did:yeying:wid_example",
  "account": {
    "chainKey": "eip155:1",
    "address": "0x0000000000000000000000000000000000000001"
  },
  "nonce": "link-nonce-unique",
  "issuedAt": "2026-08-13T00:00:00Z",
  "expiresAt": "2026-08-13T00:10:00Z",
  "identityControllerProof": {
    "algorithm": "Ed25519",
    "verificationMethod": "did:yeying:wid_example#controller-1",
    "signature": "base64url(signature)"
  },
  "accountControlProof": {
    "algorithm": "EIP-191",
    "chainKey": "eip155:1",
    "signature": "0x..."
  }
}
```

账户控制证明的消息必须绑定完整的身份 DID、链、地址、用途、nonce 和过期时间。EVM 可以使用 EIP-191；非 EVM 必须使用该链的原生签名域，不能把 EVM 签名格式扩展到其他链。

## 5. Issuer 元数据与 JWKS

Node 账户关联接口：

```text
POST /api/v1/public/identity/account-links/challenge
POST /api/v1/public/identity/account-links/verify
```

`challenge` 接收 `identity` 和 `{ chainKey, address }`，返回一次性 nonce、过期时间和待签名消息。`verify` 必须同时提交已签名的 Wallet identity document 和 EIP-191 account signature；Node 验证成功后立即消费 nonce。当前实现只支持 EVM `eip155:<chainId>`，非 EVM 必须由对应链适配器实现，不能复用 EIP-191。

### 5.1 Issuer 元数据

```json
{
  "issuer": "did:web:node.yeying.pub",
  "name": "YeYing Identity Verification",
  "credentialTypes": ["UsernameCredential", "EmailCredential"],
  "jwksUri": "https://node.yeying.pub/.well-known/jwks.json",
  "credentialStatusBatchUri": "https://node.yeying.pub/api/v1/public/identity/credentials/status",
  "credentialStatusMaxAgeSeconds": 300,
  "usernamePolicyVersion": "v1"
}
```

### 5.2 JWKS 约束

- JWK `kty` 为 `OKP`。
- `crv` 为 `Ed25519`。
- `alg` 为 `EdDSA`。
- 每个 key 有唯一 `kid`。
- issuer 轮换公钥时保留旧 key 至其签发凭证全部过期，并在撤销窗口后再移除。
- DApp 必须固定信任 issuer，不能因为 JWT 的 `iss` 自己声明就自动信任。

## 6. JWT-VC

### 6.1 用户名凭证

```json
{
  "iss": "did:web:node.yeying.pub",
  "sub": "did:yeying:wid_example",
  "jti": "urn:yeying:credential:username-01",
  "iat": 1786579200,
  "nbf": 1786579200,
  "exp": 1786665600,
  "vc": {
    "type": ["VerifiableCredential", "UsernameCredential"],
    "credentialSubject": {
      "id": "did:yeying:wid_example",
      "username": "alice",
      "usernameQualified": "alice@node.yeying.pub",
      "usernamePolicyVersion": "v1"
    },
    "credentialStatus": {
      "id": "https://node.yeying.pub/api/v1/public/identity/credentials/username-01/status",
      "type": "YeyingCredentialStatusV1"
    }
  }
}
```

### 6.2 邮箱凭证

邮箱凭证结构相同，`type` 改为 `EmailCredential`，`credentialSubject` 至少包含：

```json
{
  "id": "did:yeying:wid_example",
  "email": "person@example.com",
  "emailVerifiedAt": "2026-08-13T00:00:00Z",
  "emailVerificationMethod": "email-code-v1"
}
```

邮箱凭证只能在 `identity.email` scope 被请求并经用户确认时出示。

### 6.3 验证顺序

1. 解析 JWT header，要求 `alg=EdDSA` 和受信 `kid`。
2. 解析 `iss`，只接受配置的 issuer。
3. 通过 issuer JWKS 验证签名。
4. 校验 `sub` 是本次 presentation 的 DID。
5. 校验 `iat`、`nbf`、`exp` 和本地时钟偏差。
6. 校验 `jti` 状态不是 `revoked`、`superseded` 或 `unknown`。
7. 校验凭证类型和请求 scope 一致。
8. 校验 presentation 的 `audience`、`nonce` 和 Wallet 控制证明。

## 7. 凭证状态

### 7.1 批量查询

```http
POST /api/v1/public/identity/credentials/status
Content-Type: application/json
```

```json
{
  "issuer": "did:web:node.yeying.pub",
  "credentials": [
    "urn:yeying:credential:username-01",
    "urn:yeying:credential:email-01"
  ]
}
```

```json
{
  "issuer": "did:web:node.yeying.pub",
  "checkedAt": "2026-08-13T00:05:00Z",
  "nextUpdateAt": "2026-08-13T00:10:00Z",
  "statuses": {
    "urn:yeying:credential:username-01": "active",
    "urn:yeying:credential:email-01": "active"
  }
}
```

状态查询失败不得转化为 `active`。高风险流程的最大状态缓存时间为 5 分钟。

## 8. Identity Presentation API

### 8.1 Wallet API

web3-bs 对 DApp 暴露：

```ts
type IdentityPresentationRequest = {
  appId: string;
  audience: string;
  nonce: string;
  scopes: Array<'identity.basic' | 'identity.wallet' | 'identity.username' | 'identity.email'>;
  account?: { chainKey: string; address: string };
  issuer?: string;
  expiresAt: string;
};

type IdentityPresentation = {
  version: 1;
  holder: string;                    // did:yeying:<walletIdentityId>
  audience: string;
  nonce: string;
  issuedAt: string;
  expiresAt: string;
  scopes: string[];
  identityDocument?: SignedIdentityDocument;
  walletProof?: AccountLinkProof | WalletControlProof;
  credentials?: string[];            // compact JWT-VC strings
  proof: {
    type: 'YeyingIdentityPresentationProofV1';
    verificationMethod: string;
    purpose: 'authentication';
    proofValue: string;               // base64url Ed25519 签名
  };
};

requestIdentityPresentation(request: IdentityPresentationRequest): Promise<IdentityPresentation>;
```

web3-bs 提供 `verifyIdentityPresentation(presentation, options)` 作为 DApp 后端的基础校验辅助。它验证 presentation 的 `holder`、controller `verificationMethod`、Ed25519 `proofValue`、`audience`、`nonce`、请求 scope 和有效期。该函数不替代凭证验证：当 presentation 携带 `EmailCredential` 或 `UsernameCredential` 时，DApp 后端仍必须使用 issuer JWKS 验证 JWT-VC 签名，检查 `iss`、`sub`、credential type、`exp`/`nbf`，并调用 Node credential status 接口确认状态为 `active`。

web3-bs 另提供 `verifyIdentityPresentationCredentials(presentation, options)` 组合入口。它根据 `expectedScopes` 自动要求对应的 `EmailCredential`/`UsernameCredential`，使用 issuer 公钥验签，并在配置 `nodeBaseUrl` 时查询并强制要求 credential status 为 `active`。该入口仍不管理 DApp challenge，DApp 必须自行保存并绑定 `appId`、`audience`、`nonce`、scope 和过期时间。

Wallet 必须向用户展示 DApp origin/audience、请求 scope、issuer、用户名和邮箱是否会被读取，以及当前使用的链账户。DApp 不能通过前端字段绕过 Wallet 授权。

Wallet 的身份验证页面使用统一验证接口完成领取闭环：

1. Wallet 选取当前 `did:yeying:*` Identity 和当前链账户。
2. 调用 `POST /api/v1/public/identity/account-links/challenge`。
3. Wallet 使用 Identity document controller proof 和当前链账户的 EIP-191 签名调用 `POST /api/v1/public/identity/account-links/verify`。
4. 账户关联成功后，调用 `POST /api/v1/public/identity/verifications/request`，请求 `types: ['email', 'username']`。
5. 用户输入邮箱验证码，调用 `POST /api/v1/public/identity/verifications/confirm`。
6. Node 返回 `EmailCredential` / `UsernameCredential` 后，Wallet 加密存储到当前 Identity，presentation 才能按 scope 出示。

该流程不创建或依赖 Passport `subjectId`，也不再将旧 Passport 绑定接口作为钱包身份验证的主流程。

### 8.2 DApp 后端校验

DApp 后端必须保存 challenge 会话中的 `appId`、`audience`、`nonce`、scope 和过期时间，并逐项比较 presentation。不得接受 Wallet 返回的 scope 之外的声明。

普通 SIWE 登录不需要 `requestIdentityPresentation`。请求身份 scope 时，DApp 后端必须同时校验 Wallet 控制证明和凭证，不得只验证某一部分。

## 10. 测试向量要求

各仓库必须共享同一组 JSON fixture，至少覆盖：

- 固定身份文档 JCS 字节、Ed25519 公钥和签名。
- 正确与错误 `revision` 的文档更新。
- EVM 账户关联成功、错误链、错误地址、过期 nonce、重复 nonce。
- issuer JWKS 成功、未知 `kid`、错误 `alg`、轮换旧 key。
- UsernameCredential、EmailCredential 的签名、subject、scope、过期、撤销。
- presentation 的 audience、nonce、scope、holder、控制证明匹配和不匹配。
- 状态接口 active/revoked/superseded/unknown、超出 freshness、网络失败。
- 多身份、多链账户和账户移除不影响身份凭证。

Fixture 不包含真实邮箱、真实私钥、真实生产域名凭证或可用于生产的 token。每个仓库必须验证同一 fixture 得到相同结果和错误码。

## 11. 实施顺序

1. Wallet：身份文档、Ed25519 控制器、加密存储、账户关联 proof、多身份选择。
2. Node：issuer key/JWKS、DID 目录、用户名/邮箱凭证、状态接口。
3. web3-bs：`requestIdentityPresentation`、类型、Wallet 请求桥接、验证辅助。
4. Project/Router/Social：DID 映射、后端 presentation 验证、scope 和撤销策略。
5. 联调：先使用共享 fixture，再连接本地 Node issuer，最后做多链和恢复演练。

当前实现状态：Wallet 已完成本地身份 foundation、独立审批页面、按 scope 选择凭证和 identity controller Ed25519 presentation proof；Node 已完成独立 issuer、Ed25519 JWKS、数据库化 credential status、EVM 账户关联 proof、批量 email/username verification、凭证记录和审计落库；web3-bs 已完成浏览器 WebCrypto JWT-VC Ed25519 验签、Node credential status 查询基础和 `requestIdentityPresentation` 类型/调用入口。Wallet 凭证领取后的正式保存入口、Node DID 目录、完整 credential supersede API、Redis 限流、issuer 密钥轮换、DApp 后端 presentation 验证、共享 fixture 和真实多实例验收仍未完成，不得据此发布完整身份协议。

Node 已新增统一验证接口：`POST /api/v1/public/identity/verifications/request` 和 `POST /api/v1/public/identity/verifications/confirm`，通过 body 的 `types` 数组声明一次事务需要完成的认证集合。当前已支持 `email` 和 `username`；只有所有请求类型都成功，才返回多个凭证结果。流程要求先完成账户关联 proof，确认邮箱验证码并完成用户名 namespace 占用后签发 `EmailCredential` / `UsernameCredential`。Node 已增加身份状态迁移和数据库写入；数据库不可用时返回 `IDENTITY_STORAGE_UNAVAILABLE`，不使用内存 fallback。真实生产发布前仍需完成数据库重启验收、Redis 限流/短期缓存、审计导出和密钥轮换。

在第 1-3 步的契约测试通过前，不发布 Wallet、Node 或 web3-bs 的身份相关包。

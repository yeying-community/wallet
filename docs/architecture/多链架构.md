# 多链架构

> 状态：当前实现与演进边界
>
> 本文描述 Wallet 当前的多链适配代码、已经接通的能力和仍由上层负责的边界。能力状态以代码和测试为准；本架构不代表每条链都支持相同的交易、资产或 dApp 协议。
>
> 术语和简称见 [Wallet 核心概念](./核心概念.md)。

## 1. 范围与现状

Wallet 已从仅有 EVM 链标识演进为多链结构：通过 `chainKey` 标识当前网络，通过链适配器封装地址、交易格式、余额与 RPC 交互。当前代码包含四个适配器：

| 链 | `chainKey` 形式 | 曲线 / coin type | 当前适配器能力 |
| --- | --- | --- | --- |
| EVM | `eip155:<十进制 chainId>`，如 `eip155:1` | secp256k1 / 60 | 地址校验与展示、原生币和 ERC-20 余额、EVM 交易编码与签名组装、原始交易广播 |
| Tron | `tron:mainnet\|shasta\|nile` | secp256k1 / 195 | 地址校验、TRX/TRC-20 余额、原生转账交易构造、签名组装与广播 |
| Bitcoin | `bip122:mainnet\|testnet` | secp256k1 / 0 | 地址校验与展示、BTC 余额、原生 P2WPKH SegWit 转账、逐输入签名组装与广播 |
| Solana | `solana:mainnet-beta\|devnet\|testnet` | ed25519 / 501 | 地址校验与展示、SOL/SPL 余额、SOL/SPL 转账交易构造、签名组装与广播 |

表中表示适配器代码提供的能力，不代表所有调用入口、审批界面、Provider 标准或链上交易类型均已统一支持。Bitcoin 的 RPC 依赖网络配置；其他链的 RPC 由各自适配器解析。各链支持的参考网络和限制以对应 `chain-key-bridge.js`、交易模块及测试为准。

## 2. 分层与职责

```text
DApp / 钱包 UI / 钱包操作
          │  链相关请求与用户审批
          ▼
chainKey ──► registry.getAdapter(chainKey)
          │
          ├─ address / balance / transaction / RPC
          └─ buildUnsigned → signer 或 signing-service → assembleSigned → broadcast
```

- **`chainKey`**：使用 `<namespace>:<reference>` 格式标识链。EVM reference 是十进制 chainId，其他命名空间使用各自定义的网络 reference。`current-chain.js` 管理当前值，并仅在当前链属于 EVM 时派生 `eth_chainId` 和 `net_version` 所需的数字格式。
- **Registry**：`js/chain/registry.js` 根据命名空间分派 EVM、Tron、Solana 或 Bitcoin 适配器。未知命名空间返回 `UNSUPPORTED_CHAIN`。本地 signer 根据适配器曲线选择 secp256k1 或 ed25519 实现，并执行曲线兼容检查。
- **适配器**：`js/chain/adapters/<namespace>/` 包含链专属的地址、交易、余额和 RPC 逻辑。它负责把链交易转换为 `UnsignedTx`，并在签名后恢复链格式及广播。
- **签名编排**：`UnsignedTx` / `SignatureResult` 定义适配器和本地签名器之间的数据形态。普通本地账户经 `getSigner` 分派。MPC 账户通过 `js/chain/signing-service.js` 和现有 signing 操作编排；registry 明确返回 `MPC_SIGNER_USE_SIGNING_SERVICE`，MPC 并未统一实现为普通 `Signer`。
- **上层请求与审批**：Provider、请求路由、账户选择和审批仍由现有钱包运行时负责。适配器不是完整的链无关请求路由器，也不替上层决定权限或用户确认。

## 3. 交易签名数据流

适配器与本地 signer 使用 `js/chain/types.d.ts` 定义的契约：

1. 调用方以 `chainKey` 取得适配器，并向其提供链相关意图和上下文。
2. `buildUnsigned` 返回曲线、待签 payload 和适配器重组交易所需的 `serializeState`。账户模型链通常有一个 payload；UTXO 交易可为每个输入提供一个 payload。
3. 本地账户由 registry 选择相应曲线的 signer。EVM/Tron/Bitcoin 使用 secp256k1；Solana 使用本地 ed25519 signer。MPC 使用独立编排服务，不遵循这条本地 signer 分派路径。
4. `assembleSigned` 把签名结果放回链交易格式，随后 `broadcast` 通过该链 RPC 广播。

`SignPayload.bytes` 当前是 `0x` 十六进制字符串。ECDSA payload 表示已哈希的摘要（标注 `keccak256` 或 `sha256`）；ed25519 payload 表示待签原文。`SignaturePart` 可承载 `r‖s`、`r/s`、恢复 ID 或完整 ed25519 签名。实际字段由各适配器交易实现约定，不能把这组类型理解为 MPC 和本地签名实现已经完全收敛。

## 4. 账户与密钥

多链账户记录带有 `namespace`、`chainKey` 等链元数据；历史 EVM 账户仍由兼容逻辑映射到 EVM 默认命名空间和对应网络。钱包操作按所选链执行账户派生或导入，链专属路径和密钥转换位于各链实现中。Solana 当前有从现有 secp256k1 私钥生成 ed25519 keypair 的本地兼容辅助逻辑；这不等同于支持 ed25519 MPC，也不应据此假定各链拥有同一条助记词派生路径。

密钥加密、解锁、秘密的内存生命周期和备份边界由钱包安全层管理，链适配器不持有独立的长期密钥存储。MPC 的实现边界见[门限协议](../protocols/门限协议.md)，生产评审状态见[门限钱包架构](./门限钱包.md#生产化评审与准入条件)。

## 5. 已知边界

- **EVM 请求兼容**：EIP-1193 Provider 主要面向 EVM 语义。非 EVM 适配器存在，不代表 Tron、Bitcoin 或 Solana 已可通过 `eth_*` 请求伪装调用；各自 Provider/连接协议需要独立设计和审批。
- **能力并不对称**：适配器接口实际允许部分方法缺省。当前类型声明没有完整表达手续费估算、交易状态、统一交易摘要和地址派生能力；部分链方法只覆盖受限交易类型。UI 或调用方必须按链能力处理，不可只检查适配器是否存在。
- **交易范围受限**：Bitcoin 当前交易构造以原生 P2WPKH 转账为主；Tron 和 Solana 的具体意图类型受各自交易模块约束。通证余额查询已存在并不自动意味着相同链的通证转账、审批解释、历史索引均完备。
- **网络与 RPC**：chain reference、默认 RPC、可配置 RPC 和服务端兼容性按适配器实现。自定义网络不能仅凭语法合法就视为适配器可用。
- **地址与账户语义**：EVM/Tron/Solana 是账户模型，Bitcoin 是 UTXO 模型。统一 `address` 展示不能消除找零、输入选择、费用和多地址管理的差异。
- **签名结果约束**：恢复 ID、摘要哈希和交易序列化规则由链实现承担。适配器和 signer 必须保持对应的字节格式约定；曲线一致不代表链签名可直接互换。

## 6. 扩展约定

新增链时，应先明确网络 reference、地址与派生规则、交易/签名字节格式、RPC 与广播语义、资产查询能力、审批展示要求及 Provider 接入范围，再实现链专属适配器并注册到 `registry.js`。同时更新 `chain-key.js`、账户导入/派生路径、UI 能力守门、协议文档和链适配测试。

对尚未支持的链，建议按可验证的能力逐步开放：先完成网络识别、地址校验和只读查询，再完成离线签名与交易摘要审查，最后接入广播、状态确认、DApp 请求和恢复/迁移验收。每个阶段均需保持 EVM 回归测试通过；不能因地址和余额可读就宣传该链可安全转账。

不得把未实现的能力标成已支持；不得让非 EVM 请求沿用 EVM 交易编码、签名摘要或 `eth_sendTransaction` 审批流程。对于不同交易模型，应保留链自己的输入输出及用户可读摘要。

链账户和 Wallet Identity 使用不同主键。身份关联必须带完整 `chainKey`、地址和链专属控制证明；不能只按地址字符串或数字 chainId 判断账户身份。EVM 关联使用 EIP-191，其他链必须使用对应原生签名域。身份对象和关联证明详见[钱包身份架构](./钱包身份.md)及[钱包身份模型](../identity/钱包身份模型.md)。

## 7. 代码入口与相关文档

- `js/chain/types.d.ts`：意图、待签交易、签名结果和适配器类型。
- `js/chain/chain-key.js`、`js/chain/current-chain.js`：链标识与当前链访问器。
- `js/chain/registry.js`：适配器和本地 signer 分派。
- `js/chain/adapters/`：四种链的地址、余额、交易与 RPC 实现。
- `js/chain/signing-service.js`：链交易签名与 MPC 编排入口。
- [系统架构](./系统架构.md)：钱包整体组件和当前能力边界。
- [门限协议](../protocols/门限协议.md)：MPC 会话与密钥分片约定。

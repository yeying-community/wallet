# 链适配层设计

> 状态：架构方向设计草案，尚未进入实现。当前实现以 [钱包系统架构](./钱包系统架构.md) 为准。
>
> 本文是 [钱包未来方向](./钱包未来方向.md) §3「不兼容 EVM 的网络」的落地设计，把其中的 `ChainDefinition` / `Account` / 适配器边界具体化为可实现的接口层。目标是新增 Tron、Solana、BTC 支持时，以**适配器**方式增量演进，不破坏现有 EVM 行为。

## 1. 现状与问题

当前钱包从**签名曲线 → 地址派生 → 交易序列化 → 余额查询 → RPC → 注入 Provider → 账户模型**全链路硬编码以太坊 / ethers.js，没有任何一层是链无关抽象：

- 签名引擎 cggmp24 是编译期锁死的纯 secp256k1 门限 ECDSA。
- MPC 与本地私钥两条签名路径最终都产出 secp256k1 签名 + `ethers.Transaction` 序列化的 EVM 交易。
- 账户模型只有单个 `address` 字段，派生路径写死 `m/44'/60'`，`state.currentChainId` 隐含单一 EVM 链。

因此新增非 EVM 链属于架构级改造。本设计的取向：**先落地抽象层 + EVM 适配器，把现有逻辑逐字收敛进去（行为不变），再逐链新增适配器。** 遵循 [钱包未来方向](./钱包未来方向.md) §3.3——非 EVM 请求不得伪装成 `eth_sendTransaction`。

## 2. 设计原则

1. **零破坏**：EVM 路径逐字迁移进 `evm` 适配器，行为不变。旧账户无 `namespace` 字段时默认 `eip155`。
2. **零运行时依赖**：延续现状，新链的库（BTC / Solana）vendored 进 `lib/`，不引 npm 运行时依赖。
3. **`ChainAdapter` 与 `Signer` 正交**：适配器负责「这条链要签什么摘要、签完怎么组装」；签名引擎负责「用某曲线的份额产出签名」。MPC / 本地私钥 / 未来 ed25519-MPC 都是可替换的 `Signer`。
4. **不伪装**：非 EVM 交易走各自的链协议路径与审批摘要，不复用 EVM 交易审批器。

## 3. 核心解耦：`ChainAdapter` ⊥ `Signer`

当前 `signing.js` 把「构造以太坊交易」和「用 MPC / 本地签名」焊死。拆开后的数据流：

```text
用户 Intent
   │
   ▼
ChainAdapter.buildUnsigned()  ──►  UnsignedTx { curve, payloads[], serializeState }
   │                                         │
   │                                         ▼
   │                              Signer.sign(curve, payloads)  ──► SignatureResult { parts[] }
   │                                         │
   ▼                                         ▼
ChainAdapter.assembleSigned(UnsignedTx, SignatureResult) ──► rawTx
   │
   ▼
ChainAdapter.broadcast(rawTx)
```

- **Adapter 维度（按链）**：evm / tron / btc / solana——决定曲线、地址、序列化、广播。
- **Signer 维度（按密钥来源）**：`local-keyring`（ethers，secp256k1）、`mpc-cggmp24`（secp256k1）、`mpc-frost`（ed25519，未来）。

一个 secp256k1 份额（本地或 MPC）可同时喂给 evm / tron / btc 三个适配器，**无需重复 keygen**。Solana 需要 `mpc-frost` 这个新 `Signer` + 独立的 ed25519 份额。

  adapters/

## 5. 接口定义

延续现有约定：JSDoc typedef + `.d.ts`，ESM，零运行时依赖。

### 5.1 链无关 Intent

```js
/**
 * @typedef {Object} Intent
 * @property {'native-transfer'|'token-transfer'|'contract-call'|'sign-message'|'sign-typed-data'} type
 * @property {string} from          // 本链地址
 * @property {string} [to]
 * @property {string} [amount]      // 最小单位字符串（wei/sun/lamport/sat），不做 18 位假设
 * @property {AssetRef} [asset]     // 原生币或代币标识
 * @property {string} [data]        // EVM calldata / 其它链的等价物
 * @property {any} [raw]            // dApp 透传的原始请求，交给 adapter 解析
 */
```

### 5.2 ChainAdapter

```js
/**
 * @typedef {Object} ChainAdapter
 * // ── 元信息 ──
 * @property {'eip155'|'tron'|'solana'|'bip122'} namespace   // CAIP-2 命名空间
 * @property {'evm'|'tron'|'solana'|'utxo'} family
 * @property {'secp256k1'|'ed25519'} curve                   // 本链所需签名曲线
 * @property {number} coinType                               // BIP44: 60/195/501/0
 * @property {(net: NetworkConfig) => string} chainKey       // e.g. "eip155:1"
 *
 * // ── 地址 ──
 * @property {(publicKey: PublicKey) => string} deriveAddress
 * @property {(addr: string) => boolean} isValidAddress
 * @property {(addr: string) => string} displayAddress       // 校验和 / 缩写展示
 *
 * // ── 交易生命周期（核心解耦点）──
 * @property {(intent: Intent, ctx: ChainCtx) => Promise<UnsignedTx>} buildUnsigned
 * @property {(u: UnsignedTx, sig: SignatureResult) => string} assembleSigned   // → rawTx
 * @property {(rawTx: string, ctx: ChainCtx) => Promise<string>} broadcast      // → txHash
 * @property {(txHash: string, ctx: ChainCtx) => Promise<TxStatus>} getTxStatus
 *
 * // ── 只读 ──
 * @property {(addr: string, ctx: ChainCtx) => Promise<Balance>} getNativeBalance
 * @property {(addr: string, token: TokenRef, ctx: ChainCtx) => Promise<Balance>} getTokenBalance
 * @property {(intent: Intent, ctx: ChainCtx) => Promise<FeeEstimate>} estimateFee
 *
 * // ── 审批页可读摘要（禁止让审批器猜）──
 * @property {(intent: Intent, ctx: ChainCtx) => Promise<ApprovalSummary>} summarize
 */
```

### 5.3 UnsignedTx / SignatureResult（Signer 契约）

Adapter 与 Signer 之间唯一的交换格式，必须能同时表达 ECDSA（签摘要）和 EdDSA（签原文）：

```js
/**
 * @typedef {Object} UnsignedTx
 * @property {'secp256k1'|'ed25519'} curve
 * @property {SignPayload[]} payloads     // UTXO 每输入一个；账户模型通常一个
 * @property {any} serializeState         // adapter 内部重组 rawTx 所需的上下文
 * @property {boolean} needsRecoveryId    // secp256k1 需要 recid（见下方缺口说明）
 *
 * @typedef {Object} SignPayload
 * @property {'digest'|'message'} kind    // ECDSA=digest（已哈希）；EdDSA=message（签原文）
 * @property {Uint8Array} bytes
 * @property {'keccak256'|'sha256'|null} hashAlg   // digest 已用何算法；message 为 null
 *
 * @typedef {Object} SignatureResult
 * @property {SignaturePart[]} parts       // 与 payloads 一一对应
 *
 * @typedef {Object} SignaturePart
 * @property {Uint8Array} rs               // secp256k1: r‖s（64B）；ed25519: 完整 64B 签名
 * @property {number} [recid]              // secp256k1 only，0/1
 */

/**
 * @typedef {Object} Signer
 * @property {Set<'secp256k1'|'ed25519'>} supportedCurves
 * @property {(u: UnsignedTx, ctx: SignCtx) => Promise<SignatureResult>} sign
 */
```

> **关键缺口内置在接口里：`needsRecoveryId`。** 当前 WASM 只返回 `r‖s` 不含 recid、`v` 恒为 27。secp256k1 适配器在 `assembleSigned` 里若拿不到 recid，用已知公钥做 `ecrecover` 两候选比对补齐。该 helper 放在共享的 `secp256k1-utils.js`，ETH / BTC / Tron 三链共用，一次修复。

### 5.4 账户模型演进（最痛点，需迁移）

在现有 `{ id, walletId, name, index, derivationPath, address, encryptedPrivateKey }` 上扩展：

```js
/**
 * @typedef {Object} Account
 * @property {string} namespace           // 新增；旧数据缺省 → 'eip155'
 * @property {string} chainKey            // 新增；e.g. "eip155:1"
 * @property {PublicKey} [publicKey]      // 新增；地址派生原料（尤其 ed25519）
 * @property {number} [coinType]          // 新增
 */
```

迁移策略：`storage/account-storage.js` 读取时对缺字段的旧账户注入 `namespace:'eip155'`、`coinType:60`，写回时补全。**不动 keyring 私钥密文**，只加元数据字段。`state.currentChainId`（单值 EVM 假设）升级为 `currentChainKey`（CAIP-2），旧值 `0x1` 映射为 `eip155:1`。

### 5.5 分派入口

```js
// registry.js
export function getAdapter(chainKey)  // "eip155:1" → evmAdapter，"tron:mainnet" → tronAdapter
export function getSigner(account)    // MPC → mpc-cggmp24；本地 → local-keyring；
                                      // 按 account.namespace 的 curve 校验 signer.supportedCurves
```

## 6. EVM 适配器「零改动收敛」映射

| 现有位置 | 迁移到 |
| --- | --- |
| `signing.js` `normalizeMpcSigningPayload` / `buildMpcSignedTransaction` | `adapters/evm` 的 `buildUnsigned` / `assembleSigned`（`ethers.Transaction` 原样搬） |
| `signing.js` `signTransaction`（本地 ethers.Wallet 发送） | 拆成 `evm.buildUnsigned` + `signers/local-keyring.sign` + `evm.broadcast` |
| `signing.js` `v = recovery + 27` 逻辑 | `signers/mpc-cggmp24.sign` 产出 `{ rs, recid }`，由 evm adapter 补 v |
| `tokens.js` `eth_getBalance` / ERC20 `0x70a08231` | `evm.getNativeBalance` / `getTokenBalance` |
| `chain-handler.js` / `message-handler.js` gas 估算、receipt 轮询 | `evm.estimateFee` / `getTxStatus` |
| `network-config.js` `NETWORKS` | 加 `namespace: 'eip155'` 字段，查找函数改按 chainKey |

`request-router.js` 的 `eth_*` / `wallet_*` 路由**先保持不动**，只把内部实现指向 `getAdapter('eip155:...')`——现有 dApp、审批流、测试全部照跑。

## 7. 三条链的「填空」对照

| 能力 | EVM（已有） | Tron | BTC | Solana |
| --- | --- | --- | --- | --- |
| curve | secp256k1 | secp256k1（复用） | secp256k1（复用） | **ed25519（需新 signer）** |
| coinType | 60 | 195 | 0 | 501 |
| deriveAddress | keccak + 0x | keccak + 0x41 + Base58Check | hash160 + bech32 / Base58 | base58(ed25519 pub) |
| buildUnsigned | ethers RLP | protobuf + sha256 txID | UTXO / PSBT / 每输入 sighash | Message / VersionedTx（签原文） |
| broadcast | eth_sendRawTransaction | TronGrid HTTP | 节点 / 第三方 | sendTransaction |
| needsRecoveryId | 是 | 是 | 是 | 否（EdDSA） |
| Signer | 现有 | 复用现有 | 复用现有 | **mpc-frost 新建** |

## 8. 分阶段落地

每阶段独立可上线，不破坏前一阶段。

- **阶段 0**：建 `js/chain/` 骨架 + `types.d.ts` + registry；EVM 适配器收敛现有代码；账户模型加字段 + 迁移。验收：现有全部单测 + EVM e2e 绿。
- **阶段 1**：修 recovery-id 缺口（全链受益）。
- **阶段 2**：Tron（只读地址 / 余额 → 签名 / 审批 → 广播），复用 secp256k1 signer。
- **阶段 3**：BTC（UTXO 模型，最复杂的交易构造），复用 secp256k1 signer；dApp 注入层开始动。
- **阶段 4**：Solana——先落地 `mpc-frost` ed25519 signer（前置依赖 MPC 生产化），再 solana 适配器。

## 9. 未决点

1. **审批 UI**：各链交易差异大，`ApprovalSummary` 是统一结构 + 各 adapter 填充（推荐），还是每链独立审批页？
2. **BTC 账户模型**：UTXO 无「nonce / 单地址」概念，是否接受「一个 BTC 账户 = 一组地址（找零 / 接收）」这个更重的模型进 schema？
3. **Solana 时机**：ed25519 / FROST 依赖 MPC 先生产化（当前仍在 `dev-verification` profile），阶段 4 是否先挂 TODO 不排期？

# 知行图协议

> 状态：当前规范
>
> 定位：Wallet 对[知行图](https://github.com/yeying-community/blockchain)（记录知识单元、版本、引用与核验的公开图谱）
> 的签名支持。知行图没有资产，Wallet 在这里只做一件事：替成员保管密钥、签署知识操作。

## 1. 适用范围

本协议定义 DApp 如何让 Wallet 签署知行图的知识操作（写作、修订、核验、邀请），以及知行图成员密钥在
Wallet 里的存放方式。

它与连接协议、身份协议是并列关系：知行图不是以太坊链，没有 `eth_*` 语义，也不使用 SIWE。

## 2. 角色

| 角色 | 职责 |
| --- | --- |
| DApp 前端 | 发起连接请求，提交"意图"（谁、第几条、做什么），把 Wallet 返回的签名字节提交给知行图节点 |
| Wallet | 保管成员密钥，从意图编码出待签内容，向用户展示可读摘要，确认后签名 |
| 知行图节点 | 校验签名与操作语义，把操作写入链上，返回最终性 |

## 3. 成员密钥

| 项 | 说明 |
| --- | --- |
| 位置 | 普通钱包账户：在「账户管理 → 导入钱包」里网络选「知行图」导入。账户的 `namespace` 为 `zhixing`、`chainKey` 为 `zhixing:testnet`，地址就是 64 位十六进制 ed25519 公钥；种子与其他账户的私钥一样用钱包密码加密保存 |
| 派生 | 助记词 → BIP-39 种子（PBKDF2-HMAC-SHA512，2048 次）→ 前 32 字节作 ed25519 种子。与知行图 `node keygen` 完全相同 |
| 导入方式 | ① 助记词（可带 BIP-39 口令，即 `node keygen` 的 passphrase）；② `node keygen --encrypt` / `node encrypt-key` 写的加密密钥文件（Web3 Secret Storage v3：scrypt n=2^18 + AES-128-CTR + Keccak-256 MAC，需要文件口令）；③ `node keygen` 写的明文种子文件（64 位十六进制，可带 `# pubkey:` 注释，有就核对），或直接粘贴 64 位十六进制种子。②③ 在「私钥」页签里选文件或粘贴。几种方式得到的都是同一把密钥 |
| 用途 | 一组助记词对应一个知行图账户；把既有成员的助记词导入 Wallet，得到的就是成员原来那个链上账户 |
| 数量 | 可以导入多个知行图账户；一把种子就是一个账户（导入类型，不能派生子账户）。同一账户不能重复导入。签名用**当前选中**的知行图账户；没选中时用第一个 |
| 生命周期 | 与其他账户一样：改密时一起重加密，钱包锁定时从内存清除，可在账户管理里导出、删除。不参与 HD 钱包的备份同步（没有助记词可备份，需自己保管助记词或密钥文件） |

知行图账户虽在账户列表里，但不是 EVM 账户：`eth_accounts` 不会返回它，选中知行图网络时
钱包也不转发 EVM JSON-RPC。网页只能通过下面的 `zhixing_*` 方法使用它。

## 4. 标准流程

1. DApp 调用 `zhixing_requestAccounts`。
2. Wallet 展示来源，用户确认连接（本协议单独授权，不与 EVM 站点授权混在一起）。
3. DApp 调用 `zhixing_signKnowledgeOp`，参数是**意图**。
4. Wallet 自己把意图编码成待签内容，展示可读摘要（例如"核验单元 #8 的 v2：通过"），用户确认或拒绝。
5. Wallet 返回 `signed`（待签内容 ‖ 签名 的十六进制）。
6. DApp 把 `signed` 原样 POST 到知行图节点的 `/knowledge`。

### 4.1 Provider API

```ts
// 已授权时返回公钥；未授权返回 []。不弹窗、不需要解锁。
type ZhixingAccountsResult = string[];   // ['<64 位十六进制 ed25519 公钥>']

// 请求连接。首次弹窗确认。
type ZhixingRequestAccountsResult = string[];

// 签署一条知识操作。
type ZhixingSignRequest = {
  actor: string;   // 知行图账户编号（u64，十进制字符串）
  nonce: string;   // 该账户的操作序号（u64，十进制字符串）
  action: KnowledgeOpAction;
};

type KnowledgeOpAction =
  | { type: 'create'; layer: 'foundation' | 'explanation' | 'scenario' | 'application'; domain: number;
      bodies: Array<{ lang: string; hash: string }>; source: Source; cites: Cite[] }
  | { type: 'publish'; unit: number; bodies: Array<{ lang: string; hash: string }>; source: Source; cites: Cite[] }
  | { type: 'verify'; unit: number; version: number; verdict: 'pass' | 'needs-revision'; noteHash?: string }
  | { type: 'invite'; pubkey: string };

type Source = { type: 'human' } | { type: 'model'; id: string } | { type: 'model-verified'; id: string };
type Cite = { unit: number; version: number; kind: 'basis' | 'see-also' | 'supersedes' };

type ZhixingSignResult = {
  signed: string;   // 待签内容 ‖ 64 字节签名，十六进制；可直接 POST /knowledge
  address: string;  // 签名所用的知行图公钥
};
```

### 4.2 编码与签名

```
op  = actor:u64 ‖ action ‖ nonce:u64          (大端)
sig = ed25519( "zhixing-knowledge-op-v1" ‖ op )
signed = op ‖ sig
```

与知行图节点（`node/src/codec.rs`）逐字节一致。Wallet 侧编码由 `tests/zhixing-op.test.mjs` 对照知行图浏览器
签名器（其本身已对照 Rust 节点逐字节检验）的输出检验。

### 4.3 为什么 DApp 只递意图

DApp **不**把待签字节交给 Wallet。若允许，弹窗里显示的内容就可能与实际签的内容不同。
Wallet 从意图自行编码，摘要与签名必然一致——用户看到的就是签下去的。

## 5. 错误语义

| 错误 | 含义 | DApp 应做什么 |
| --- | --- | --- |
| `4001` | 用户在审批里拒绝 | 不要自动重试；提示用户 |
| `4100` | 本站尚未连接知行图密钥 | 先调用 `zhixing_requestAccounts` |
| `4900` | Wallet 里还没有知行图账户 | 提示用户在 Wallet「账户管理 → 导入钱包」里选择「知行图」导入 |
| `-32602` | 意图不合法（未知操作、字段越界、哈希长度不对等），在弹窗前就被拒绝 | 修正参数；消息里以 `ZHIXING_` 开头的部分说明原因 |
| `-32601` | 钱包版本不支持这些方法 | 提示升级钱包 |

## 6. 用户界面要求

- 连接请求：展示站点来源与将要分享的公钥；说明"网站只能看到公钥，看不到私钥或助记词"。
- 签名请求：展示操作的可读摘要（动作、对象、版本、结论）与影响（"这条核验记录会永久保存在链上"）；
  邀请操作须说明担保责任："被担保人作恶被查实时，担保人会连带受罚"。
- 不得只显示原始字节或十六进制。

## 7. 权限与撤销

知行图连接按站点单独记录（`zhixing_authorized_sites`），不与 EVM 站点授权混在一起。
用户可在 Wallet「网站管理」里看到已授权的网站（标注连接的知行图账户）并随时撤销。授权记在连接时选中的知行图账户名下，换了账户需要重新连接。撤销后该网站的
`zhixing_accounts` 返回空数组、`zhixing_signKnowledgeOp` 返回 `4100`。
